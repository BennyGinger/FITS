# FITS Pipeline – Architecture Context

## Overview

The FITS pipeline processes microscopy experiments in a structured, reproducible way.
The pipeline operates on **ExperimentState** objects, which represent the processing state of a single experiment unit (usually a single image series).

The pipeline is composed of independent workflow steps (e.g. `convert`, `segment`).
Each step takes a list of `ExperimentState` objects and returns updated states.

Steps are designed to be:

* deterministic
* restartable
* filesystem-based
* resilient to folder reorganization

---

# Core Concepts

## Experiment Unit

An experiment unit corresponds to a **workdir folder** containing all artifacts produced by the pipeline for a single raw image (or series).

Example layout:

```
Run3_test/
├── control/
│   ├── c3z1t1v3.nd2
│   └── c3z1t1v3_s1/
│       ├── fits_array.tif
│       ├── fits_mask.tif
│       └── experiment_state.json
```

Here:

```
workdir = Run3_test/control/c3z1t1v3_s1
```

---

# Path Anchoring Model

## Durable Anchor: `workdir`

All persisted paths inside `ExperimentState` are **relative to `workdir`**.

Examples stored in state:

```
original_image_rel = ../c3z1t1v3.nd2
image_rel = fits_array.tif
masks_rel = fits_mask.tif
```

Absolute paths are reconstructed at runtime:

```
original_image = workdir / original_image_rel
image = workdir / image_rel
masks = workdir / masks_rel
```

This design ensures that **moving experiment folders does not break the state**.

Example: adding a new folder level

```
Run3_test/
└── replicate1/
    └── control/
        ├── c3z1t1v3.nd2
        └── c3z1t1v3_s1/
```

Because paths are anchored to `workdir`, the state remains valid.

---

# Runtime Context

The pipeline runtime provides an **ExecutionContext** accessible through:

```
get_ctx()
```

The context stores runtime-only information such as:

```
run_dir
user_name
logging settings
execution mode
```

`run_dir` is **NOT persisted in ExperimentState**.

It is used only for:

* discovery scope
* condition/tag extraction
* display paths in logs

---

# Display Paths

For logging purposes, paths are displayed relative to `run_dir` when possible.

Example:

```
absolute path:
/data/Run3_test/replicate1/control/c3z1t1v3_s1/fits_mask.tif

display path:
replicate1/control/c3z1t1v3_s1/fits_mask.tif
```

This is handled by:

```
ExperimentState.workdir_relative(run_dir)
```

which returns:

```
workdir.relative_to(run_dir)
```

with safe fallback to absolute paths.

This helper is **only used for logging and error messages**.

It must never be used to resolve filesystem paths.

---

# ExperimentState

`ExperimentState` is the durable representation of pipeline progress.

Key attributes:

```
workdir: Path
original_image_rel: Path
image_rel: Path | None
masks_rel: Path | None
completed_steps: tuple[str, ...]
last_error: tuple[str, str] | None
updated_at: datetime
```

Important rules:

* `workdir` is the **persistent anchor**
* all artifact paths are **relative to workdir**
* runtime context (run_dir etc.) is **never stored in state**

---

# State Discovery

Saved states are discovered using:

```
discover_saved_states(run_dir)
```

which scans for:

```
experiment_state.json
```

Each discovered state uses:

```
workdir = json_path.parent
```

The discovered folder is **authoritative**.

The saved JSON may contain informational fields (like `workdir`) for debugging, but the filesystem location always wins.

---

# Raw Experiment Initialization

Raw experiments are initialized before conversion.

Raw state creation:

```
workdir = raw_file.parent
original_image_rel = raw_file.name
```

No derived artifacts exist yet.

Example raw state:

```
Run3_test/control/c3z1t1v3.nd2
```

---

# Convert Step

`convert` creates the workdir and the FITS array.

Example:

```
c3z1t1v3.nd2
→
c3z1t1v3_s1/
    fits_array.tif
```

After conversion:

```
workdir = c3z1t1v3_s1
image_rel = fits_array.tif
original_image_rel = ../c3z1t1v3.nd2
```

`fits_array.tif` becomes the canonical downstream image representation used by all later pipeline steps.

Convert may:

* export all channels
* export a subset of channels
* optionally apply Z-projection

Convert is also the only step that has access to the original raw channel layout.
Because of that, it writes structural channel identity metadata into the private TIFF payload:

```
source_channel_indices
source_channel_count
```

Meaning:

```
source_channel_count
    total number of channels in the original raw image

source_channel_indices
    mapping from exported FITS channel index -> original source channel index
```

Example:

```id="dummy1"
original raw channels: [0, 1, 2]
exported FITS channels: [1, 2]

source_channel_count = 3
source_channel_indices = [1, 2]
```

These fields are the structural anchor for downstream channel-aware processing.

---

# Segment Step

`segment` reads the converted array and writes segmentation masks:

```
fits_mask.tif
```

State update:

```
masks_rel = fits_mask.tif
completed_steps += ("segment",)
```

The segment step may run on only a subset of exported channels.

Requested segmentation channels are resolved from the converted TIFF labels, but stable identity is recovered through:

```
source_channel_indices
```

stored in the input TIFF private metadata.

This allows segment metadata to be keyed by **original source channel index**, not by mutable labels and not by local Cellpose subset order.

Segment private metadata is step-aware and channel-aware.

Target shape:

```
payload["segment"] = {
    "dist": "...",
    "version": "...",
    "timestamp": "...",
    "channels": {
        "<source_channel_index>": {
            ...
        }
    }
}
```

This means:

* step provenance remains at the step level
* channel-specific metadata is stored under `channels`
* repeated segment runs may replace one channel entry while preserving the others

The mask file currently stores the segmentation output for one or more channels.

Future versions will support true **mask array merging**, where existing masks are read, merged channel-wise, and re-saved without losing already valid channels.

# Metadata Architecture

Metadata handling is implemented in **fits_io.metadata** and is explicitly layered.

The metadata pipeline is built from three independent stages.

## 1. Context Resolution

```
resolve_build_context(...)
```

This stage:

* resolves effective channel labels
* determines channel count
* resolves axis order
* extracts resolution and timing from the reader
* initializes the base private payload

The result is a **MetadataBuildContext** describing the output artifact.

For converted TIFFs, the base payload may already include:

```
source_channel_indices
source_channel_count
```

which are then propagated automatically by later steps unless explicitly changed.

---

## 2. Private Metadata Payload

```
build_private_payload(...)
```

This stage updates the pipeline metadata payload.

It is responsible for:

* step name generation
* status updates
* user tracking
* z-projection metadata
* provenance insertion
* merging step metadata

This metadata is stored in the private TIFF tag.

Important behavior:

* unrelated top-level metadata is preserved
* provenance updates preserve existing step metadata
* step metadata can merge nested channel dictionaries under:

```
payload[step_name]["channels"]
```

This is what makes incremental channel-aware segment metadata possible.

---

## 3. TIFF / ImageJ Metadata Assembly

```
build_tiff_metadata(...)
```

This stage assembles the final metadata models used when writing the TIFF:

* channel metadata
* stack metadata
* resolution metadata
* ImageJ info block
* encoded private metadata tags

The result is a `TiffMetadata` object used by the writer.

---

# Metadata Design Principles

Two metadata categories are clearly separated.

## ImageJ / Viewer Metadata

Viewer-facing metadata used by ImageJ and other tools.

Examples:

```
Labels
axes
resolution
color mode
LUTs
info summary
```

These fields describe how the image should be interpreted and displayed.

Channel labels are **human-readable annotations** and may change over time.

Labels are not structural identifiers.

---

## Private Pipeline Metadata

Pipeline metadata is stored in a private TIFF tag.

Examples:

```
status
user_name
z_projection_method
provenance steps
source_channel_indices
source_channel_count
```

This metadata tracks pipeline state and processing history.

For channel-aware steps such as `segment`, private metadata may also contain:

```
payload[step_name]["channels"]
```

keyed by original source channel index.

---

# Channel Identity Model

Channel labels are **not stable identifiers**.

Labels may change after conversion (for example when users rename channels).

To maintain structural consistency across the pipeline, channel identity is anchored to **source channel indices**.

Current structural fields:

```
source_channel_indices
source_channel_count
```

This allows:

* partial channel export during convert
* later reintroduction of missing channels
* channel-aware downstream processing
* safe mapping from exported TIFF channels back to original raw channels

For segment specifically, this enables metadata keyed by original source channel index rather than by label.

Future mask-specific metadata may also introduce:

```
segmented_source_channel_indices
```

or equivalent channel-aware mask tracking structures.

---

# Workflow Execution

Workflow steps follow the pattern:

```
run_step(settings, states, ...)
```

Steps:

* read artifacts from state
* compute results
* write outputs
* return updated states

All filesystem resolution uses:

```
state.workdir
```

---

# Design Principles

### Deterministic execution

Each step reads only declared inputs and writes deterministic outputs.

---

### Restartability

Steps are skipped when already completed:

```
state.completed_steps
```

Note:
for channel-aware steps such as future incremental `segment`, step-level completion alone may become too coarse.
Channel coverage metadata may also need to be inspected.

---

### Filesystem-first design

Artifacts are stored as files:

```
fits_array.tif
fits_mask.tif
```

State only tracks metadata.

---

### Folder reorganization safety

Experiment folders may be reorganized after processing.

Because paths are anchored to `workdir`, the pipeline can rediscover and continue processing without breaking.

---

# Summary

Durable state:

```
ExperimentState
    workdir anchor
    relative artifact paths
```

Runtime environment:

```
ExecutionContext
    run_dir
    execution settings
```

Metadata pipeline:

```
resolve_build_context
→ build_private_payload
→ build_tiff_metadata
```

Structural channel identity:

```
source_channel_indices
source_channel_count
```

Filesystem layout remains the **source of truth**.

# Coding Style Requirement

Do not spread function parameters across multiple lines.

Avoid:

```
def myfunc(
    param1,
    param2,
    param3,
):
```

Prefer:

```
def myfunc(param1, param2, param3):
```

Apply the same rule to function calls whenever reasonably possible.

Same with imports.

Avoid:

```
import (
 module1,
 module2,
 ...
)
```

Prefer:

```
import module1, module2
```
